# Domain docs

How engineering skills should use this repo's domain documentation.

## Before exploring

Read the root `GLOSSARY.md` and relevant decisions in `docs/adr/`, if they exist. If a file is absent, proceed without flagging its absence. Create domain docs when terms or decisions are actually resolved.

## Layout

This is a single-context repo. Keep one `GLOSSARY.md` at the root and architecture decision records in `docs/adr/`.

## Vocabulary and decisions

Use the glossary's terms in issues, proposals, tests, and code. If a needed concept is missing, reconsider the term or note the gap for domain modeling. Explicitly flag any proposal that conflicts with an existing ADR.
